# Combat Lab — Experiment Protocol

**Status:** PROVISIONAL RECOVERY LAW · NOT IMMUTABLE ARCHITECTURE

This protocol exists to keep Combat Lab exploratory, Owner-centered and operationally autonomous without letting implementation momentum, repository state or machine qualification become research authority.

It is itself falsifiable. If Owner evidence or repeated use shows that a rule harms discovery, change the rule.

## 1. Start from live evidence, not inherited direction

Before substantial work:

- inspect current `main`, active experiment refs, `rehearsal/current` and deployed provenance;
- recover the newest relevant Owner judgement and Owner-observed behavior;
- distinguish demonstrated findings from hypotheses, candidates and historical plans;
- treat repository documentation as a description of current facts, not as permission to continue an old roadmap.

Do not continue a mechanism, branch or campaign merely because it is current, green, documented or easy to extend.

A canonical state file may record an active question after that question has actually been selected. It must not turn a completed campaign's final bullet into automatic future authority.

## 2. Know which research mode you are in

Combat Lab uses different modes. Confusing them was a major historical failure.

### Discovery mode

Default for an unresolved frontier.

Build or compare sufficiently whole, deliberately divergent organisms/world situations so that a valuable phenomenon can actually appear.

The goal is:

> discover where there is something worth explaining.

Clean attribution is secondary.

### Diagnostic / attribution mode

Use after a valuable or problematic phenomenon exists and the question is why it happens.

A diagnostic cell may be artificial, tiny and machine-heavy.

Its PASS qualifies only the narrow fact it tested. It does not automatically become:

- a foundation;
- a parent implementation;
- the next research question;
- part of the future organism.

When a diagnostic campaign ends, authority returns to the wider discovery/construction question that caused the diagnosis.

### Serious construction mode

Use when the evidence or explicit Owner direction says the current prostheses are no longer the target and a qualitatively more serious whole must be built.

This mode may take substantial time.

Do not satisfy a request for a serious organism by assembling a chain of diagnostic fixtures and presenting their local PASSes as delivered progress.

Use findings as design knowledge. Reuse code only when the new whole actually benefits from it.

### Lab / infrastructure mode

Use only for capabilities that improve experimentation itself: input, camera, deployment, causal observation, exact authoring, reset, provenance and similar neutral machinery.

Infrastructure must not encode the answer to a research hypothesis merely for convenience.

## 3. State the question before code

Before opening a substantial lane, state compactly:

- the uncertainty;
- the relevant baseline or reference;
- what would be unmistakably different if the hypothesis matters;
- what evidence can answer it;
- what would falsify or stop the work;
- which assumptions or parts are deliberately temporary.

For a discovery specimen, the discriminator must be phenomenon-level.

For a diagnostic cell, the discriminator may be mechanistic.

Do not silently substitute one for the other.

## 4. Preserve the correct baseline

A branch-local improvement is not automatically project progress.

Before calling something better, ask what it is being compared against.

Relevant baselines may include:

- the last Owner-observed specimen;
- the qualitative capability the Owner requested;
- a sibling organism;
- a deliberately simpler control.

Do not let:

> new implementation -> self-created pathology -> partial repair

masquerade as progress over the actual project baseline.

Before Owner exposure, explicitly ask:

> is this qualitatively more informative or capable than the relevant thing the Owner already rejected or outgrew?

## 5. Discovery is phenomenon-first

When opening an unresolved frontier, prefer whole situations capable of producing different behavior over clean parameter theater.

The question is normally closer to:

> what does this organism/world relation make the Owner naturally start doing or noticing?

than:

> did parameter X reduce metric Y?

A discovery specimen should expose a possibility surface rather than one pre-authored solution.

Depending on the frontier, useful possibilities may include:

- approach / retreat / angle change;
- hold / yield / displace;
- route choice / bypass / use of clutter or open space;
- threaten / interrupt / commit;
- exploit reach, cover, obstruction, body size or terrain;
- create, relieve or intentionally enter pressure.

Mechanism cells are allowed to be much narrower. They simply remain mechanism evidence.

## 6. Diagnostics do not own the future

This rule closes the failure that produced the M1 -> R1 -> D1 -> S1 tunnel.

A diagnostic PASS means:

> this narrow explanation/candidate survived its declared falsifiers.

It does **not** mean:

> build the next adjacent mechanism on top of it.

At diagnostic closure:

1. preserve the finding;
2. separate any useful donor property from the fixture;
3. return to the wider question;
4. reassess whether the diagnosis changes what is worth building.

A completed diagnostic campaign does not select the next frontier by default.

After a bounded campaign closes, the normal research state is:

> **FRONTIER OPEN**

until a separate frontier selection deliberately chooses otherwise.

## 7. Serious construction must remain whole

When the project has accumulated enough evidence to justify a serious build, build a coherent whole.

Do not force the new whole to be the sum of old diagnostic modules.

The design may re-derive, simplify or reject previous mechanisms.

During long construction, periodically compare the emerging whole against:

- the original qualitative target;
- the relevant Owner baseline;
- the possibility surface it is supposed to create.

If internal metrics improve while the whole remains qualitatively unchanged, do not call that delivery.

## 8. Evidence boundaries

Machine evidence can qualify:

- deterministic helpers;
- geometry and numerical properties;
- runtime health;
- input plumbing;
- causal traces;
- reproducibility;
- provenance;
- exact deployment.

Machine evidence cannot qualify:

- whether a whole organism is genuinely interesting;
- feel, weight, responsiveness or mastery;
- possibility richness;
- desire to keep experimenting or playing;
- whether an interaction belongs in the long-term project.

Those require Owner judgement when the question is actually experiential.

## 9. Owner attention is scarce research evidence

Do not use the Owner as a debugger for a question the agent can answer itself.

Before requesting Owner rehearsal:

- finish machine-answerable checks yourself;
- ensure obvious runtime defects will not dominate;
- ensure the specimen is genuinely different at the phenomenon level from the relevant rejected/outgrown baseline;
- ensure the remaining question actually needs human experiential judgement.

A diagnostic mechanism becoming easier to inspect is not, by itself, a reason for Owner rehearsal.

## 10. Lab freedom is part of the apparatus

Where relevant, preserve:

- live intervention;
- exact numeric authoring;
- broad and extreme ranges;
- intentional break regimes;
- strange combinations;
- causal inspection;
- continued observation of damaged or surprising states.

Do not silently clamp, ghost, despawn or simplify the world merely to keep the preferred experiment valid.

Safety rails are justified only by real program/runtime risk and must remain visible.

## 11. Implementation has no automatic continuity rights

Code may survive for several different reasons, but none is automatic.

A finished lane may become:

- **discarded implementation, finding retained**;
- **bounded donor material**;
- **continued current specimen**, because its actual research question is still alive;
- **promoted neutral infrastructure**, after concrete use shows that it expands experimental freedom without encoding one hypothesis;
- **unresolved**, because more evidence is genuinely required.

Do not make DELETE a religion.

Do not make PRESERVE a religion either.

Most importantly:

> isolated mechanism PASS does not grant parent/foundation status.

Any implementation inheritance requires a separate concrete justification from the new consumer.

## 12. Repository and CI are servants, not research authority

Repository structure must make experimentation easier, not decide what the project believes.

Current topology intent:

- `main` — current neutral Lab state and durable research truth;
- at most one active authoring/experiment lane unless real simultaneous comparison requires more;
- `rehearsal/current` — deployment pointer only, never an authoring branch or research authority;
- forensic archive refs — evidence reachability only.

CI may assert:

- syntax;
- declared tests;
- browser/runtime execution;
- deterministic mechanical facts;
- provenance/deployment integrity.

CI must **not** assert semantic roadmap text such as:

- `NEXT = ...`;
- a specific future campaign;
- that a diagnostic result is a foundation;
- that a product/experience claim is true.

Green CI can prove repository consistency. It cannot legitimize a research direction.

## 13. Deployment discipline

Experimental pushes do not become public merely because they exist.

Public rehearsal is explicit:

- select the exact candidate SHA;
- move `rehearsal/current` to it;
- require a fresh ordinary check;
- deploy that exact checked SHA;
- verify public provenance.

After rejection or completion, move the pointer deliberately to the intended public state.

The Owner should never need to manage branches, SHAs, CI or deployment unless tooling genuinely prevents the agent from doing a specific required operation.

## 14. Meaning of "kontynuuj"

A short Owner command authorizes continued work on the current objective.

It does not mean:

- execute the last roadmap bullet;
- extend the current implementation by inertia;
- stop every few minutes and ask for another `kontynuuj`.

During one turn:

1. recover the live state;
2. identify the highest-value unresolved uncertainty;
3. check whether new evidence invalidates the current plan;
4. execute a substantial coherent block of work;
5. finish the block cleanly enough to report a meaningful checkpoint.

The Owner should not have to act as the agent's scheduler or context keeper.

## 15. Refoundation and donor recovery

A clean execution reset is allowed whenever accumulated implementation constrains discovery.

Preserve evidence, not architectural obligation.

Historical or sibling-project material may be recovered only for a concrete current need:

1. identify the exact property or finding;
2. recover its provenance;
3. transplant or re-derive the minimum useful part;
4. re-test it in the new context.

Do not browse old code merely because it exists.

## Working invariant

> **Discover valuable phenomena first; diagnose them when needed; build serious wholes from knowledge rather than from the accidental ancestry of diagnostic fixtures.**
