# Combat Lab — Experiment Protocol

## 1. Start with a question, not a prototype lineage

Every experiment begins with one concrete uncertainty. It exists only to create evidence about that uncertainty. It is not automatically a seed for the next system.

## 2. Declare expiry before implementation

Before coding, state:

- the question;
- the smallest apparatus needed;
- the falsifiers;
- what evidence ends the experiment;
- which parts are deliberately fake, crude or temporary.

## 3. Disposable is the default

After the question is answered, the normal action is to delete the experiment from the active tree.

Preserve the finding when useful. Do not preserve implementation because deleting it feels wasteful.

## 4. Promotion requires a separate burden of proof

A mechanism may survive only if a later need shows reuse is materially better than rebuilding it.

Passing tests, commit count, age and sunk cost do not satisfy this burden.

Promotion must state what exact capability is preserved, what evidence shows it generalizes beyond its original fixture, what future design freedom it does not constrain, and why keeping it is epistemically cheaper than recreating it.

## 5. A request to go forward ends prototype authority

When the Owner says the current thing is a crude prosthesis and asks for a substantially more serious organism, the correct response is not to make the prosthesis more internally sophisticated.

The old fixture may remain briefly as a measuring instrument. It loses product authority immediately.

## 6. Internal falsifier != Owner specimen

A narrow fixture may be ugly and artificial when that helps answer one causal question. Such a fixture must never be presented as the payoff for a long integration campaign.

Owner attention is requested only when the thing being shown is itself the object that needs experiential judgement.

## 7. Lab freedom is part of the apparatus

Where relevant, the Owner must be able to perturb live state, use exact/extreme values, push break regimes, create strange combinations, inspect causes and continue from damaged or surprising states.

Safety rails are justified only by actual program/runtime risk and must be explicit.

## 8. Knowledge survives more easily than code

Prefer:

> experiment → finding → new question → fresh implementation

over:

> experiment → permanent subsystem → more permanent subsystem.

## 9. Mandatory end-of-run classification

Every research run ends as one of:

- **DELETE**
- **REBUILD FROM FINDING**
- **PROMOTE WITH JUSTIFICATION**
- **UNRESOLVED — MORE EVIDENCE REQUIRED**

“Keep it around just in case” is not a valid classification.
